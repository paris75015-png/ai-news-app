# 共通の編集方針（3系統すべてに適用）

国内深掘り・国際深掘り・AI日報のすべてに適用する規則。各系統の方針より前に読む。

---

## 1. 文体と可読性（最優先）

分量を削ることより、読み手の認知負荷を下げることを優先する。
同じ情報量でも「頭に入りやすい日本語」にすることが、この仕組みで最も重視する品質である。

- **一文一義。一文は短く。** 目安として40〜60字で一度切る。**60字を超える文を残さない。**
- **係り受けは浅く。** 「〜であり、〜だが、〜のため、〜という」と節を連結しない。接続のたびに文を割る。
- **枠順を毎回固定する。** 読み手が次に何が来るか予測できる状態を保つ。
- **前提復習は独立した短文で。** 継続ストーリーの背景を地の文に長く編み込まない。短い文で先に置いてから本日の差分に入る。
- **うるさくしない。** 強調は使わない。本文に記号を散らさない。
- 迷ったら「短い文に割る」を選ぶ。

### 指示語を本文に書かない

「前提を3行で置く。」「補注を置く。」は、この方針が書き手に出している内部指示であって、読者に見せる文言ではない。**本文に絶対に書かない。**

- ✗ 「前提を3行で置く。米国とイスラエルは2月28日に……」
- ✓ 「米国とイスラエルは2月28日に対イラン攻撃を開始した。以降、断続的な戦闘が続いてきた。」

「補注」も、**海外発の固有名詞（政党名・人名・制度名・機関名）が初出したときに短い説明を添えること**を指す仕様語である。段落の見出しではない。素直に事実から書き始める。

---

## 2. 2つの階層 — 深掘りと短信

全記事を同じ書式で書かない。**深掘り**と**短信**の2階層に分ける。JSON の `depth` がこれにあたる。

| 階層 | `depth` | 本文 | 構成 |
|---|---|---|---|
| **深掘り** | `deep` | **600〜800字** | `body` にラベル付きの節を並べる。`summary` は null |
| **短信** | `brief` | **150〜250字** | `summary` に平文。`body` は null。節のラベルは付けない |

- **階層はスコアと独立している。** 高スコアの続報が短信になることは正常である。
- **「情報が足りないから短信」ではない。** その事案に割くべき分量が150〜250字である、という編集判断である。書ける材料があっても短信の枠を超えない。
- **記事が少ない日に、既存記事を膨らませて総量を維持しない。** 深さではなく幅に倒す。
- **スロット埋めの水増しは禁止。** 重要度の低い記事を入れるくらいなら件数を減らす。ただし下限を割る場合は `productionNote` に理由を書く。

### 深掘りの節の構成

`body` の節は、系統ごとに決まった順で並べる。順番を入れ替えない。

- 新規の事案 … `概要兼背景` → `今後の影響` →（国際のみ）`日本・アジアへの含意` →（該当時）`視点の差`
- 継続の事案 … `概要兼背景` を `本日の動き` に置き換える。歴史的経緯・既知の構図は省略し、**前回からの差分のみ**を書く

`今後の影響` は2文。1文目は直接的・短期的な帰結、2文目は構造的・中期的な含意。役割を分ける。

## 3. 出典の確度ラベル

**「記事本文を取得できなかった」ことと「その媒体を出典に書けない」ことは別である。**
`sources[].access` に、その媒体から実際に何を確認できたかを3段階で記録する。

| `access` | 意味 | 数値・固有名詞の引用 |
|---|---|---|
| `body` | 記事本文を取得した | 可 |
| `excerpt` | 検索結果の抜粋で該当箇所を確認した | 可。ただし抜粋に現れた範囲に限る |
| `headline` | 本当に見出ししか得られていない | **不可。数字を書かない** |

**検索結果の抜粋は見出しではない。** 抜粋に金額・日付・人名が現れていれば、それは確認済みの事実であり引用してよい。抜粋で読めたものを `headline` と過小申告しない。
逆に、見出しにしかない情報から本文の数字を推測して書くことは禁止する。

### 本文が取れない媒体は、再掲載先を1回探す

通信社配信や有力紙の記事は、他媒体・ポータルに全文が転載されていることが多い。
**「見出しのみ」と判定する前に、転載先を1回探す。**

転載先で本文を読んだ場合、`outlet` には**元の発信元名**を書き、`via` に確認経路を書く。

```json
{ "outlet": "共同通信", "via": "中日新聞Web", "access": "body", "date": "2026-09-18" }
```

### 一次発信元へ遡る

**アグリゲータ記事を見つけたら、そこで止まらない。** 記事本文はほぼ必ず元の発信元を明示している（「Bloomberg reported」「according to The Information」）。その発信元名を検索し直し、**元の報道を `outlet` に書く。**

- ✗ `"outlet": "TechStartups"`
- ✓ `"outlet": "Bloomberg", "via": "TechCrunch"`

**数字の初出者を必ず確認する。** ある推計値が話題になっている場合、それを最初に出したのが誰かを1回は調べる。
出典の正確性のためだけでなく、「その数字を最初に出したのが日本の媒体だった」というケースが最高級の【視点の差】素材になるためである。

### 使ってはならない媒体

- コンテンツファーム／自動転載サイト
- 他媒体の再構成にすぎないテック系ブログを**一次の代わりに**使うこと。これらで事象を知るのは構わないが、必ず元記事に遡って出典を書き換える
- 匿名運営のニュースまとめ、AI生成と思われる記事

## 4. 当日性の検証

採用候補の各記事について、以下を確認する。**ここを飛ばすことが過去の最大の失敗要因である。**

### 配信日と事象日を分ける（最重要）

- **配信日** … その記事がいつ公開されたか。`sources[].date` に書くのはこちら
- **事象日** … 発表・会見・決定・発生が実際にいつ起きたか。**本文に書く日付はこちら**

この2つは頻繁にずれる。18日12時配信の記事が「17日に発表した」と書いていることは日常的にある。
**配信日を本文の日付に流用しない。** 記事本文に事象日が明記されていない場合は、本文で日付を断定せず「〜と報じられた」と書く。

**日付をずらして書かない。** 「16日に明らかにした」を「17日までに」と書き換えるのは事実の改変にあたる。

### 報道段階を区別する

- 交渉中・未署名の案件を、完了した事実として書かない
- 匿名筋報道を「発表した」に格上げしない
- 金額が複数媒体で割れている案件を、確定値のように書かない

### 「発表日」と「実施日／取得日」を区別する

- **世論調査** … 調査実施日が発表の1〜2週間前であることが多い。実施日が3日以上前なら当日の新展開に入れない
- **統計・被害集計** … 「自治体が◯日に明らかにした」の◯日が発表日
- **企業発表・裁判** … 記者会見日と資料公開日がずれることがある

### 数量の分類を確認する

合計値を書く場合、その数値がどのカテゴリの合計かを原典で確認する。
「住家被害2314棟」と「浸水2314棟」は別の意味になりうる。

### 人名・肩書を確認する

人名を書く場合、氏名の表記と肩書を原記事で確認する。
「向井秀明 社長室長」と「向井英明 CEO補佐」のような取り違えは、数字と違って一見して気づけない。
確認できない場合は人名を出さず、「同社は〜と説明した」と書く。

### 他媒体に帰属させるときは直接確認する

「◯◯紙は△△としている」という形で他媒体の呼称・フレーミングを引用する場合、**その媒体の記事を直接確認してから帰属させる。** 記憶や印象で媒体名を当てない。

## 5. 継続ストーリーの扱い

進展型ニュースを採用する際は、**何が新事実なのかを言語化してから採用する。** 新事実が言えないなら採用しない。

### 前提復習の定型文を禁止する

直近3日分の過去分を読んでいる以上、その3日に登場した系統について読者は前提を持っている。
同一の背景文を毎日置くと、続報1件あたり60〜100字が固定的に失われる。

| 同一系統の直近登場 | 前提復習 |
|---|---|
| 直近3日以内に登場 | **書かない。** 必要なら経緯行1本（20字以内。例「経緯は9/18版参照」） |
| 4日以上前／初登場 | 2文まで置いてよい |

**同一の発言・発表を3日連続で引かない。** ある人物の警告や報告を、初日は本記事、翌日は背景、翌々日も背景として引くと、一つの出来事が3日分の紙面を運ぶ。背景として引けるのは1回までとする。

### 続報の階層判定

**続報は原則として短信で扱う。** 初期点数を超える内容があるときだけ深掘りに上げる。

**初期点数** … 直近3日分の過去分において、同一系統に付いた最高スコア。`continuity.previousScore` に記録する。
4日以上登場していない系統は再エントリー扱いとし、新規記事と同じ基準で採点する。

**深掘りに上げるには、軌道が変わったことを一文で言語化できなければならない。** それを `continuity.note` に書く。スコアの数値だけで判定しない。

昇格してよい例:

- 方針の反転（「外国救助隊を拒否」→「限定受入に転換」）
- 段階の進行（協議開始 → 合意署名、検討 → 発動）
- 当事者の交代・離脱
- 波及先の拡大（二国間の問題が第三国の措置を引き出した）

昇格事由にならない例:

- 「警告した」「懸念を表明した」「協議した」「報じられた」
- 前日と同じ主体が、前日と同じ趣旨を繰り返した

**数値の更新だけでは初期点数を超えない。** 死者数・被害額・避難者数の増加は、それ自体では昇格事由にならない。桁が変わる、あるいは想定の枠組みが崩れる場合に限る。

- ✗ 死者98人 → 270人 → 362人 → 633人。毎日「不可逆性が増した」として昇格させる
- ✓ 初日のみ深掘り。以降は短信で数値を更新する。救助方針の転換など性格が変わった日だけ深掘りに戻す

## 6. スコア

各記事を0〜100点で採点する。

### 系統ごとに尺度が独立している

**AI日報・国内深掘り・国際深掘りの90点は、それぞれ基準が違う。**
教科ごとの偏差値と同じで、系統をまたいで同じ点数を比べてはいけない。
画面でも並べて比較させない。帯記号の境目は `src/article.js` の `SCORE_BANDS` にある。

| 系統 | ◆◆◆ | ◆◆ | ◆ | 下限 |
|---|---|---|---|---|
| 国内深掘り | S80以上 | S70〜79 | S60〜69 | S60未満は載せない |
| 国際深掘り | S90以上 | S80〜89 | S70〜79 | S70未満は載せない |
| AI日報 | S80以上 | S65〜79 | S50〜64 | — |

### 共通の判断軸（優先順位順）

1. **不可逆性** … 閣議決定・法案成立・首脳合意・死者発生など、後戻りできない事象
2. **影響範囲の広さ** … 金利・為替・主要法改正など、生活コストや権利に直接波及するもの
3. **新規性** … 今日初めて報じられた、または状況が大きく動いたか
4. **構造的意味** … 単発に見えても制度的・地政学的な転換点になるか
5. **媒体間の合致** … 複数の主要媒体が同じ事象を一面級で扱っているか

軸1は他軸に優先する。迷ったら「1年後に振り返って、どちらが起きなかったことにできないか」で並べ替える。

### 明示的に外す基準

PV／話題性の高さ、見出しの派手さ、芸能・SNS炎上、通常の決算発表（重大な戦略転換を伴う場合は別）、株価の日次変動のみの記事。

## 7. 誤情報への注意

誤報は避けるが、フレーミングや解釈の方向性は「考え方の選択肢」として提示する価値がある。
確信度が低い解釈は根拠の質を明示する。媒体間でフレームが分かれる場合は、どちらかを正解とせず両論の存在を示す。

### 因果の重心を取り違えない

市場や政策の動きは、各紙が筆頭に挙げている要因を確認してから書く。二次的な要因を主因のように書かない。

**価格・相場・数値が動いた記事では、各媒体が挙げている要因を最低2つ本文に書く。** 要因を1つも書かずに影響論だけを展開しない。

> 失敗実例（2026-08-19）: 長期金利2.945%の記事で、数値と起点（1996年10月）は完全に正確だったが、各社が揃って挙げていた3要因——中東情勢による原油高、日銀の早期利上げ観測、高市政権の財政拡張路線——がすべて落ち、日銀総裁人事の話だけになっていた。当日の値動きの説明になっていない。

### 波及の向きを確認する

「他へ波及するか」と書く前に、その事象が波及の**起点**なのか**到達点**なのかを原典で確認する。

> 失敗実例（同版）: 新潟の概算金4割安について「東日本の他産地がこの水準に引きずられるかが焦点」と書いたが、実際は鹿児島が先行して2割安で決まり、九州・四国の早場米も前年割れした後に、最大産地の新潟へ波及した局面だった。向きが逆になっている。

### 訳語に注意する

専門用語に日本語の訳語を括弧書きで添えるときは、**その訳語が実在するか確認する。** 定訳がなければ括弧を付けず、説明文で処理する。

- ✗ 「チョークポイント（絞首点）」← 誤訳。造語しない
- ✓ 「チョークポイント。海上輸送が一点に集中する隘路を指す」

## 8. 制作記録は紙面に出さない

収集範囲・到達できた媒体・除外した話題とその理由・件数は、**すべて `productionNote` に入れる。**
読む画面には出さない。

従来はこれを「※注記」として紙面の先頭に600字置いていたが、読み物の冒頭に作業ログが来る形になっていた。
品質管理の記録としては有用なので、機械で読める形で保持し、表示場所だけを分ける。

```json
"productionNote": {
  "reachedOutlets": ["NHK", "読売新聞", "共同通信"],
  "unreachedOutlets": ["産経新聞"],
  "excluded": [{ "topic": "イラン情勢", "reason": "戦争の続報。方針により国際深掘りでは短信に限定" }],
  "counts": { "deep": 7, "brief": 7, "essays": 2, "chars": 6200 },
  "text": "前回発行は9/18。9/19は休日で未発行。…"
}
```

`counts.chars` は記事本文（`body` と `summary`）の合計文字数。空白を除いて数える。

## 9. 出力の手順

### Step A — 過去分と他系統を読む（収集前に必ず実行）

1. `public/data/archive/` から、**自分の系統の直近3日分**を読む。採用済みの見出しを一覧化する
2. **自分より先に走った系統の当日分**を読む（[README](README.md) の実行順）。そこに出ている話題は落とす
3. 前回からの空白期間を把握する。空白が長い場合、取りこぼし全件の穴埋めはしない。今もっとも重要なものを優先し、`productionNote` に書く

これにより、毎回まっさらな状態で開始してよい。前の実行を覚えている必要はない。

### Step B — 収集・検証・採点

各系統の方針に従う。

**サブエージェント（Agent ツール）に委譲しない。自分で調べて自分で書く。**
バックグラウンドのエージェントに渡すと、結果が返る前に定期実行のセッションが終わり、
記事ができていても push されない。2026-09-21 に2回発生した。
調査も執筆も検証も、この1つのセッションの中で完結させる。

### Step C — JSON を書く

`public/data/{stream}.json` に `Edition` 形式で書く。型は [`src/article.js`](../src/article.js) にある。
同じ内容を `public/data/archive/{YYYY-MM-DD}-{stream}.json` にも書く。

- `date` は**必ず次のコマンドの出力をそのまま使う**。自分で計算しない

  ```bash
  TZ=Asia/Tokyo date +%F
  ```

  クラウドの実行環境は UTC で動いている。朝7時台の実行は UTC ではまだ前日なので、
  頭の中で「今日」を決めると1日ずれる。**2026-09-21 の初回実行で実際にずれた。**
  アーカイブのファイル名もこの値を使う
- `model` には実行時に指定されたモデル名をそのまま書く。指定がなければ自己申告し `（自己申告）` を付す。**自己申告は信頼できない**ので、モデル間比較の一次記録として扱わない
- `id` は記事ごとに一意であればよい（見出しのハッシュなど）

### Step D — commit して push

```
git add public/data
git commit -m "{系統名} {YYYY-MM-DD}"
git push
```

**`git pull --rebase` を先に実行する。** 同じ日に別の系統が先に push している。

## 10. 出力前の自己検証（共通分）

確定する直前に機械的に確認する。1つでも × があれば書き直してから push する。
系統ごとの追加項目は各方針にある。

**確度**

- [ ] 「発表した」と書いた全箇所で、当事者が実際に公式発表したか確認したか
- [ ] 交渉中・未署名の案件を、完了した事実として書いていないか
- [ ] `sources[].access` が、実際に確認できた粒度と一致しているか。抜粋で読めたものを `headline` と過小申告していないか
- [ ] `access: "headline"` の媒体から取った数字を本文に書いていないか
- [ ] 本文が取れなかった主要媒体について、再掲載先を1回探したか
- [ ] `outlet` にアグリゲータ名が残っていないか。一次発信元に遡って書き換えたか
- [ ] 話題の推計値について、その初出者を1回は確認したか
- [ ] 他媒体に帰属させた箇所は、その媒体の記事を直接確認したか
- [ ] 合計値を書いた箇所で、その数値がどのカテゴリの合計かを原典で確認したか
- [ ] 本文に書いた人名の氏名表記と肩書を、原記事で確認したか

**当日性**

- [ ] 本文に書いた日付が、記事の配信日ではなく**事象日**であることを確認したか
- [ ] `sources[].date` に配信日を入れたか
- [ ] 直近3日分と重複していないか。進展型は新事実を言語化できるか
- [ ] **先に走った系統の当日分を読んで、重複を落としたか**
- [ ] 主要記事について、同日中の関連続報を1回チェックしたか

**形式**

- [ ] 見出しは全件30字以内か（数えたか）
- [ ] **60字を超える文が残っていないか。**多重接続の文はないか
